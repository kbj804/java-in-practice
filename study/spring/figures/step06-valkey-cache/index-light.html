Spring Fig 6 · 동네 목록 캐시: 몰린 요청, 이벤트로 고치기, 늦게 들어온 옛 값, 동시 만료

동네 최신 글 목록을 Valkey 에 둡니다. 목록 키(region:{id}:latest)에는 글 ID 만, 제목은 글마다 post:{id} 에 둡니다. 위는 단계마다 누가 누구에게 요청을 보냈는지, 가운데는 Valkey 키 세 개와 PostgreSQL 커넥션 풀, 그 아래는 이 방식이 쓰는 Valkey 명령, 맨 아래는 시간축입니다.

0.00초
가 · 락 없이 cache-aside
없으면 각자 DB 에서 읽어 캐시에 넣는다

    목록 DB 쿼리–
    가장 늦은 응답–
    받은 사람–
    나 · single-flight (SET NX PX 락)
    없으면 락을 잡은 한 명만 DB 에서 다시 만들고, 나머지는 20ms 마다 다시 읽는다

      목록 DB 쿼리–
      가장 늦은 응답–
      받은 사람–
      다 · 이벤트로 고치기 (목록 키는 지우지 않음)
      새 글 ZADD (키가 있을 때만) · 제목 수정 DEL post:{id} · 블라인드 ZREM + DEL

        목록 다시 만들기–
        화면 목록–
        같은 이벤트 2번 더–
        라 · 한 번만 지움
        제목이 바뀌면 DEL post:7 한 번. 늦게 들어온 옛 값은 TTL 이 지운다

          옛 제목이 보인 시간–
          옛 값을 지운 것–
          마 · 지연 이중 삭제 (1초 뒤 한 번 더)
          DEL post:7 하고 1초 뒤 한 번 더 DEL. 그 사이에 들어온 옛 값을 지운다

            옛 제목이 보인 시간–
            옛 값을 지운 것–
            가 · EX 600 (모두 같은 10분)
            SET post:{id} {…} EX 600

              만료가 몰린 시간–
              그동안 초당 DB 읽기–
              나 · EX 600 + 지터 0~120초
              SET post:{id} {…} EX (600 + 무작위 0~120)

                만료가 몰린 시간–
                그동안 초당 DB 읽기–
                • 파란 화살표 · 이번 단계에 오간 요청
                • 빨간 화살표 · 같은 일을 여러 번, 옛 값을 넣음
                • 목록 칸 · 들어 있는 글 ID
                • 목록 칸 · 이번 단계에 새로 들어온 글
                • 커넥션 칸 · 쓰는 중

                앞의 세 장면은 실제 테스트(FeedCacheExperimentTest, PostgreSQL · RabbitMQ · Valkey Testcontainers) 결과이고, 그림의 단계 모델로 계산한 마지막 상태와 같습니다. 동시에 몰린 150명: 목록 키가 빈 순간 락 없이 cache-aside 로 읽으면 150명이 모두 DB 로 가서 커넥션 10개 앞에 줄을 서고(목록 쿼리 150번, 가장 늦은 응답 790ms), SET NX PX 락으로 한 명만 다시 만들게 하면 목록 쿼리는 1번입니다. 이벤트로 고치기: 새 글은 ZADD, 제목 수정은 DEL post:{id}, 블라인드는 ZREM 으로 고쳐서 목록을 DB 로 다시 만들 일이 없고, 같은 이벤트가 두 번 와도 Sorted Set 이라 한 번만 들어갑니다. 늦게 들어온 옛 값: DB 를 읽고 멈춘 요청이 삭제 뒤에 옛 제목을 넣으면, 한 번만 지우는 방식은 TTL 이 지울 때까지 옛 제목이 남고, 1초 뒤 한 번 더 지우면 1초 안에 사라집니다. TTL 동시 만료는 실험이 아니라 계산입니다. 스페이스로 재생/멈춤, ← →로 한 단계씩 옮깁니다.
